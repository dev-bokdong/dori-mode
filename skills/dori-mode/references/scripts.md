# Scripts

`scripts/` is a bun + TypeScript package with one CLI, `dori`. Every external command runs as an argv array; nothing builds a shell string.

## Install and test

```sh
cd skills/dori-mode/scripts
bun install          # runtime dependencies plus types and tsc
bun link             # puts `dori` on your PATH
bun test             # behavior tests with fake herdr/git/gh; nothing real is touched
bunx tsc --noEmit    # typecheck
```

Needs: bun 1.3+, herdr, git, and the GitHub CLI (`gh`) for `merged`/`closed` signals (npm for `published`). The `command`, `file` and `url` signals need nothing extra. The full list of signal kinds is in `sessions.md`. The host guard reads `sysctl`, `memory_pressure` and `df` on macOS; on Linux it reads `/proc/loadavg` and `df`, and memory and swap read as unknown.

The old fixed keys (`holdLanes5hPct`, `holdLanes7dPct`, `brief5hPct`, `brief7dPct`, `nearReset5hMin`, `nearResetHoldLanes5hPct`, `account`) are ignored with one `CONFIG_QUOTA_KEYS_REMOVED` warning. `quota`, `status` and `doctor` show the summed headroom; `supervise` reads usage every `pollMin` minutes into `<stateDir>/claude-quota.json` for `status` and `LAUNCH_READY`. Hooks are argv templates for your messenger CLI. `{thread}`, `{text}` and `{key}` are filled into each argument separately, so the text stays one argument whatever it contains.

dori has no task-tracker integration: it knows lanes, PRs and threads only. Keeping a tracker in step with lanes is the lead's job through the tracker's own tools (an MCP like any other). A config written for an older version may still hold `memoryCheck.toodoMcp`, `memoryCheck.toodoTokenFile` or `ciToodoWorkspaces`, and a lane file `toodoTask`; they are ignored.

### Always-on behavior

These used to be boolean config flags; they are always on now. A config that still carries one of the old keys (`sweepSnapshot`, `sweepTask`, `superviseTasks`, `operations`, `threadArchive`, `ciFollowUp`, `toodoReconcile`, `claimDelivery`, `branchCleanup`, `eventSources`, `schedules`, `laneReports`) loads as before: the key is ignored and named once on stderr as `CONFIG_FLAGS_REMOVED <keys> in <path>`, so it can be deleted at leisure.

- **Sweep snapshot** (`supervise`): each 30 s sweep round takes one `herdr pane list` per machine, shared by watch, guard, dead-panes, recover, freshness and quota; screen and process reads are reused while a pane's herdr `revision` is unchanged, and the reads of changed lanes run at most 4 at a time per machine.
- **Supervisor tasks** (`supervise`): there is no single loop but four independent tasks: `inbound` (Discord catch-up and the gateway heartbeat), `delivery` (owner delay, ack and unhandled notices, then lead delivery), `sweeps` (the 30 s sweep round) and `polling` (waits, GitHub, event sources and lane reports), so inbound, owner notices and lead delivery never wait behind a slow sweep. Every sweep is tracked by the watchdog. A task whose pass runs past 5 min is reported by name as `TASK_STALLED <task>` (logged and queued for the lead; a stalled `delivery` also posts one line to the first `discordChannels` entry) while the other three keep working, and `TASK_RECOVERED <task>` is logged when it moves again; past 15 min it withholds `WATCHDOG=1` as `task:<task>`, so systemd restarts the supervisor. Each task's first pass is logged as `STARTUP_TIMINGS first-<task>` (`first-sweep` for the sweeps).
- **Operations** (`close`, `watch`, `supervise`): every effect of a close (worktree removal, `hooks.threadDone`, thread archive, branch deletes, tab or pane close) is an operation row (`operations.json`; on the sqlite store the `operations` table of `supervisor.sqlite`), written durably as attempted before the effect and settled by a read-back after it. An interrupted close is resumed by the next watcher pass without repeating an effect, or stops as urgent `OPERATION_AMBIGUOUS`; see `dori close` and `dori ops`.
- **Thread archive** (`close`, `watch`, `supervise`): after `hooks.threadDone`, a close archives the lane's Discord thread (`discord:<channel>/<thread>`) through the API and reads it back `archived: true`, only once no other open lane shares the thread (a shared thread stays open until its last lane closes). It is the `<key>/thread-archive/<thread>` operation. Needs `DORI_DISCORD_TOKEN`; without it the receipt says `thread archive skipped`. A refused archive is a receipt line (`thread <id> not archived: ...`), not a refused close.
- **CI follow-up** (`supervise`): after each GitHub poll, every open PR of an open lane (its `Done =` names the PR, or a lane worktree has its branch) is followed. Failing checks at the head SHA queue one lane message with an ID (`ci-<repo>-<n>-<sha7>`; `lane-messages.json`, on the sqlite store the `lane_messages` table), typed once (send-text, one Enter) only while the lane's pane exists, runs an agent, is idle and the lane is not paused; the lane confirms with `dori report ack <id>`. A message still queued (busy, paused, missing pane) or delivered without an ack `ciConfirmMin` after it was queued is one urgent `LANE_MESSAGE_UNCONFIRMED`. A green PR is read again (`gh pr view`) and merged only when its lane has a done claim (`dori claim-done` or a remote `done` report) made after the head commit, and it is open, into `ciMergeBase`, never into `main`, still at the polled head, not a draft, every check green and GitHub says MERGEABLE and CLEAN: `gh pr merge <n> --merge --match-head-commit <sha>`, never `--admin`, then digest `CI_MERGED ... merge=<sha>`. A conflicting PR whose own lane is live (not paused, its pane exists and runs an agent, busy or idle; an unreadable pane list counts as live) gets one lane message asking it to rebase onto `ciMergeBase` itself (`rebase-<repo>-<n>-<sha7>`, delivered and confirmed like the CI message, superseded once the PR stops conflicting at that head) and no merge lane. Once that lane is paused, closed or dead (no pane, pane missing, no agent in it), the PR gets a merge lane (`merge-<repo>-<n>`, a detached worktree of the PR branch under `worktreeRoot`, the same thread, `Done = merged <repo>#<n>`) that resolves, waits for green and merges; when the host or quota gate holds or the launch fails, urgent `CI_CONFLICT`. Merges and launches are operations (`<lane>/merge/<repo>#<n>@<sha>`, `<lane>/merge-lane/...`), so a restart never repeats one; a merge GitHub refuses 3 times is urgent `OPERATION_FAILED`. `GH_PR * checks_failing` and `GH_PR * conflicting` are digest unless `eventPolicy` names them. Lanes still wait on their own CI.
- **Issue close** (`launch`, `adopt`, `supervise`): a brief line `issue: owner/repo#N` (a line of its own, optionally a list item) binds the lane to that GitHub issue (the `ghIssue` registry field); a malformed value refuses the launch. While the lane's PR is open, CI follow-up plans a `<key>/close-issue/<issue>@<repo>#<n>` operation, so the issue is still closed when the lane closes before the merge. Once a poll sees that PR merged and `gh pr view` confirms it MERGED into `ciMergeBase`, dori runs `gh issue close <N> --comment "Closed by dori: <repo>#<n> (lane <key>) is merged into <base> as <sha>. <url>"` once (read back with `gh issue view`) and logs digest `CI_ISSUE_CLOSED`. An issue already closed is verified without a comment; a PR merged into another base never closes it; a close GitHub refuses 3 times is urgent `OPERATION_FAILED`.
- **Claim delivery** (`watch`, `supervise`): a done claim's `closeAfterMin` window starts when its `LANE_DONE_CLAIMED` reaches the lead, not at the claim. The watcher enqueues the claim as `done-claim:<key>:<claim time>` and records `claim.deliveredAt` on the first pass that reads it delivered: logged to a warm lead, or in a cold start that has confirmed (a batch logged for a cold start that has not confirmed does not count). Until then the claim waits, however late. `dori watch`, with no supervisor, counts printing the line as delivery; a claim announced by an older dori (no event id) keeps its window from the claim. A lane whose brief declares `autoClose: machine` claims as `LANE_AUTO_CLAIMED` and closes as `LANE_AUTO_CLOSED`, both digest, with the window from the claim, so it closes with no lead wake (objections stay urgent `LANE_NOT_DONE`).
- **Branch cleanup** (`close`, `watch`, `supervise`): SHA-bound branch cleanup (design 4.3). For each `merged <owner/repo>#N` Done signal the close reads the PR's head branch, head SHA and base (`gh pr view`), and for each lane worktree (the lane's own cwd included when it is a linked worktree) it looks up a PR merged from that worktree's branch into `ciMergeBase` (`gh pr list --state merged --head <b>`), so no special Done line is needed; a worktree on that branch is removed only while its HEAD is exactly the merged head, otherwise it stays (`branch-bound worktree <wt> kept: ...`, never swept). After the worktrees it re-reads the local ref, the worktree list and the remote ref, and deletes the local branch with a compare-and-delete (`git update-ref -d refs/heads/<b> <sha>`) only when the local ref and the remote ref (if it still exists) still point at the merged head and the branch is not checked out, not protected (`main`, `master`, `dev`, `develop`, `trunk`, `release`, `staging`, `production` or the PR's base) and not named by another open lane's Done line. Anything else keeps the branch with one receipt line, `branch <b> kept: <why>` (a commit after the merge names both SHAs). Each delete is a `<key>/branch-delete/<owner/repo>#N@<sha>` row, planned with its git dir before any worktree goes, so an interrupted close resumes it. Before the local branch, the remote branch is deleted under the same rules with a lease on the merged head (`git push --force-with-lease=refs/heads/<b>:<sha> <remote> :refs/heads/<b>`, a `remote-branch-delete` row); one already gone is skipped. A lane cwd is removed only at exactly a merged head; dirty, it is kept. A done-claimed lane whose PR is confirmed merged (a verified `merge` operation of the lane, i.e. CI_MERGED; a `merged` Done signal reading MERGED; or a PR merged into `ciMergeBase` from a lane worktree's branch at its HEAD) closes on the next watcher pass instead of waiting out the claim window. Remote lanes are skipped.
- **Event sources** (`supervise`, `status`): events come from registered sources. The built-ins (`discord`, `github`, `sweeps`, `waits`, and `emit`, the spool `dori emit` writes) record their last event and errors; the `poll`, `webhook` and `file` sources in `<stateDir>/sources.json` (`dori source`) run in the polling task. Every event goes through the journal's dedupe and `eventPolicy`. A source that throws is isolated: it is shown as failing in `dori status` and `/status`, one digest `SOURCE_FAILED <name> <type>: <error>` is journaled when it starts failing (built-ins report their errors as before), and the other sources keep running. Per-source state is in `<stateDir>/sources-status.json`.
- **Schedules** (`supervise`, `status`): the `schedule` sources managed by `dori schedule` run in the polling task (scheduled jobs inside Dori instead of system cron). Each run is an operation row in the store (`schedule:<name>/schedule-run/<slot>`), so a job's last run survives restarts, its next run follows from it, and no slot runs twice; `dori status` lists every job with its next run.
- **Lane reports** (`report`, `watch`, `supervise`): structured lane reports (design 3.3). `dori report <key> <kind> --text T` writes one row (see `dori report`) and the supervisor routes it in its 5 s polling pass: `question` and `blocked` become urgent `LANE_REPORT <key> <kind> <text>`, `milestone` a `LANE_REPORT` classed by `eventPolicy` (`LANE_REPORT * milestone` and `LANE_REPORT * progress` are `lead-digest` unless `eventPolicy` names them), `progress` is posted to the lane's thread through `hooks.threadReply` (no hook, no thread or a failed post: a digest `LANE_REPORT ... progress` instead), and `done` is the lane's done claim, as `dori claim-done`. A remote lane's `[REPORT]` lines are read as a sequence: every line on its screen not acted on before is acted on, top to bottom, each told apart by (lane, line hash, first-seen) in the `remoteReportsSeen` registry field, so two reports printed between two polls both arrive, in order; a lane read by an older dori (newest line only) replays nothing. `launch` gives a new local lane the `dori report` footer (report with `dori report`, never by typing into the lead's pane; done is `dori report <key> done --evidence E`) and records `reportVia: "cli"` on it; remote lanes keep the `[REPORT]` footer. Such a lane's `[REPORT]` lines found in the lead's pane are counted by the `lead-pane` sweep: each distinct line once, as `leadPaneViolations` on the lane and a digest `LANE_PANE_VIOLATION <key> <count> <line>` (the sweep reads the lead's pane only while such a lane is open). Lanes on the older footer keep typing `[REPORT]` lines, which keep working.

## Library modules

The CLI is a thin layer over typed modules you can import in your own scripts:

| `src/messenger/telegram.ts` | `Telegram`: send, edit, typing, `sendMessageDraft` streaming with a `Thinking…` start, forum topics (create, rename, close, reopen), HTML tables |
| `src/messenger/discord.ts` | `Discord`: send without pings, edit, typing, threads (start, rename, archive); gateway presence |
| `src/messenger/discord-commands.ts` | `DiscordCommands`: register guild `/quota`, `/status` and `/emergency`, defer private replies, enforce owner access and format bounded results |

| `src/status.ts` | `collectStatus` / `renderStatus`: the no-LLM one-screen summary behind `dori status` and `/status` |
| `src/gateway-status.ts` | the supervisor's `gateway-status.json` heartbeat in stateDir (written every loop, about 5 s); doctor and status read it |
| `src/claude-quota.ts` | `lookupQuotaResults(agentDir?)`: pi-quota through senpi's native auth storage (defaults to `~/.omo/agent`); `claudeUsage`, `gateVerdict`, `launchQuotaHold`, `claudeQuotaTick`, `quotaReport`: the Claude headroom gate over every account |
| `src/messenger/typing.ts` | `typingWhile`: show typing while a piece of work runs, stop when it ends |

### Discord `/status`

## Commands

### `dori doctor`

Read-only health check; it never starts, stops or edits anything and never prints a token. Each line is `OK`, `WARN` or `FAIL` and a non-OK line is followed by `fix: <exact command or step>`. Exit 0 when nothing is FAIL, otherwise 1. Every probe is bounded (5 s per command, 10 s per Discord request).

Checks: `herdr-server` and `dori-supervisor` enabled and active; a legacy `dori-presence` unit or stray `dori presence` process (WARN, double-gateway risk); herdr reachable with one server process; the supervisor unit's WorkingDirectory, `defaultCwd` and `stateDir` exist; config keys (`leadPane`, `laneWorkspace`, `defaultModel`, `discordChannels`, the discord ids) and the lead pane in herdr; `DORI_DISCORD_TOKEN` in `~/.dori/env` works (`GET /users/@me`), the bot is in the guild, every `discordChannels` id is readable; the Message Content flag on `/applications/@me` (WARN with the Developer Portal step); `/quota` and `/status` registered in the guild (WARN: restart the supervisor); the lead's memory (`memoryCheck`): `human.md` found and within `maxKb` (WARN when it is missing or over); the gateway heartbeat is fresh and connected (FAIL if missing or older than 60 s); `gh` installed and authenticated, `jq`, `bun`; free disk against `guard.diskFreeMinGb` (WARN). `dori setup` runs it at the end and prints the report.

### `dori status [--json | --page N]`

`--page N` prints the same page as `/status page:N`. `--json` lists every working lane; each lane carries `report`, its latest `dori report` row (highest seq: `id`, `seq`, `kind`, `text`, `evidence`, `at` and, once routed, `consumedAt` and `route`), read from `lane-reports.json` or the `lane_reports` table opened read-only.

One screen, read-only, no LLM, times in KST (fixed +09:00). Line 1 is a summary: `DORI OK 10-21 09:53 KST | lanes 1 | waits 1`, or `DORI PROBLEM ... | <what>` (a service not active/enabled, an active legacy `dori-presence`, a gateway that is not live, GitHub poll failures, no trusted `githubIssueAuthors`, a missing or unknown lead). Then the lead (pane, warm or cold against `cacheTtlMin`, idle time, last context tokens against `leadContextCapTokens`), one `! ...` line per problem, and one `ok:` line naming the healthy parts (services, gateway, GitHub poll, issue watching; the legacy unit counts as healthy when inactive). When the last 24 h journaled any event, `wakes 24h <n>, <calls> calls/wake` and `kinds 24h: <kind> <events>ev <wakes>w <calls>c/w, ...` follow: per event kind (as `eventPolicy` names it), the events journaled, the lead wakes it triggered and the model calls per wake. A wake is a delivery that starts a lead turn (events appended for an idle warm lead, or a confirmed cold start, `(restart)` when it carried no event); it is triggered by its urgent kinds, else by its overdue digest kinds, and counts once for each. Its calls are the assistant records the lead session wrote from the wake to the next wake, counted when that next wake starts (`?` until then). Wakes live in the store (`lead_wakes`, 30 days; the json store appends `lead-wakes.jsonl`); `--json` gives the full table under `events`. Working lanes follow (key, short model such as `opus-5-5`, age, repo when the Done signal or worktree names it, and `#PR` only for an explicit `/pull/N` or `pr view N` in the Done signal, since a `(#N)` in a lane title may be a task or issue id; last progress line), then pending `dori wait`s with their fire time in KST and time left (the epoch in a `[ $(date +%s) -ge N ]` signal), else `on signal, timeout <KST>` from the wait's `deadline` (its timeout, not its fire time), else the clipped signal, and the wait's note. Lists are capped with `+N more` so the text stays under 1900 characters. `--json` prints the same data (additive fields: lane `repo`/`pr`, wait `note`). The supervisor answers the Discord `/status` command with this text, which the command wraps in a code block.

A `sources: <name>[(<type>)] <last kind> <age>, ...` line follows (built-ins first; `-` for a source with no event yet, `!failing` while it fails), each failing source is a problem line `! source <name> failing since <age>: <error>`, and an unreadable `sources.json` is one too. A `schedules: <name> next <MM-DD HH:MM> KST (<time> left)[ last <result>], ...` line lists every scheduled job (`waiting for a heavy slot` while a due heavy job waits; the last result is shown unless it was `ok` or `emitted`). The same text is `/status` in Discord.

### `dori repos add <owner/repo>` / `dori repos remove <owner/repo>` / `dori repos list`
Manages this machine's extra GitHub repos in `<stateDir>/github-repos.json`, a private JSON array written atomically. Names are trimmed, lowercased, validated as `owner/repo`, and deduplicated; URLs and paths are rejected. Adding an existing repo or removing an absent one is safe. Commands print the resulting JSON list. The supervisor rereads it each polling tick, so changes need no restart; repos inferred from registry lanes are watched separately and are not removed by this command.

`dori setup` asks for an optional comma- or whitespace-separated list after choosing the state directory. A fresh setup defaults to empty; reruns show and preserve the current list. Use `dori repos remove` to remove individual entries.

The supervisor uses conditional `gh api` requests and keeps ETags and last-seen PR snapshots in `<stateDir>/github-events.json` (on the sqlite store: its `gh_*` tables). Keep this file and the existing supervisor queue/log across restarts. Lane PRs come from merged signals or GitHub worktree/head branches. `GH_PR owner/repo#N kind detail url` lines for lane check failures, merged/closed PRs, conflicts and other people's comments/reviews are urgent; opened PRs, green checks and other updates wait for the next urgent delivery. Bots, the authenticated user and the repository owner are filtered from review/comment wakes. `HOST_GITHUB` failure notes are digest-only and limited to one per repo per 15 minutes.

The same poll lists each repo's issues (`issues?state=all`, ETag-cached; pull requests in that list are skipped). The first issue poll of a repo, including a repo that was already watched before this feature, records a baseline and emits nothing. After that, a new open issue or a reopened one by a `githubIssueAuthors` login emits urgent `GH_ISSUE owner/repo#N opened|reopened author=<login> <url>`; any other author emits digest `GH_ISSUE_UNTRUSTED` with the same fields. Lines never carry the title or body, which are untrusted text. Event IDs are `github-issue:<repo>#N:opened` and `...:reopened:<count>`, so a restart or a crash before the snapshot save does not deliver twice. An issue poll failure counts as the repo's poll failure (`HOST_GITHUB`), and the next good poll clears it.

### `dori launch <key> --title T --brief FILE --done "..." [--thread REF] [--model M] [--cwd DIR] [--machine LABEL|ID] [--pane ID | --workspace ID] [--share-thread] [--allow-repo-mismatch] [--ignore-quota --reason TEXT]`
Opens a lane: appends the footer to the brief, opens a tab, starts the agent, and after 20 seconds checks it: `STARTUP_ERROR` on a known failure in the pane, `STARTUP_OK` when herdr reports the agent working, or idle with no failure on its screen, and `STARTUP_UNCONFIRMED` (with the last lines) otherwise. Exit 3 on anything but `STARTUP_OK`.

Launch validates the key, duplicate registration, Done syntax and thread sharing before checking the gates, so an invalid request never enters HOLD. A lane on a Claude subscription model then passes the Claude quota gate: over a `quotaGate` hold line it prints `HOLD quota <mode>: <reasons>, resets <KST>` and exits 4 without starting an agent. The host guard (memory, disk, pane count) is checked here too. On any HOLD, launch prints `HOLD <reasons>` and `QUEUED <key> (<n> waiting; dori hold list)`, atomically adds the request and raises the blocked flag in `launch-hold.json`, and exits 4; the queue entry leaves when that lane launches or is dropped. If `launch-hold.json` can't be parsed or has the wrong shape, it's moved aside to `launch-hold.json.corrupt-<ms>` and `LAUNCH_HOLD_CORRUPT moved <path> to <aside>: <error>; continuing blocked with an empty queue` goes to stderr. Launches stay held until the guard clears, and any queued work in the old file has to be launched again by hand. A single bad queue entry is dropped instead (`LAUNCH_HOLD_INVALID_ENTRY`), and the valid ones stay. `--ignore-quota` lifts only the Claude gate (only on the owner's explicit word) and needs `--reason TEXT`, or it exits 1: it prints `OWNER_NOTICE lane <key> is launching past the Claude quota gate with --ignore-quota (...); reason: <text>` for the lead to relay and appends the bypass to `<stateDir>/quota-bypass.jsonl`. With `guard.panesMax` at 0 or below every launch prints `LAUNCH_WARN`.
Before writing the footer or creating a tab or agent, launch rechecks admission and reserves its key, thread and checkout under one lock shared with adopt. A pending launch is recorded as paused with `launchReservation`, preventing automatic recovery from spawning it. Success replaces the reservation with the launched lane; failure before agent admission releases only its own reservation. A process crash or registration failure after agent admission leaves the paused reservation visible for inspection instead of silently starting another agent; the pane and tab are recorded before agent admission.
Placement checks (launch and adopt, skipped for remote lanes and directories outside git): another open lane on the same thread is refused unless `--share-thread` (recorded as `threadSharedWith`); a cwd in the same checkout as another open local lane is refused; a cwd whose git remotes name none of the `Done =` repos is refused unless `--allow-repo-mismatch`. A local lane starts with `DORI_LANE_KEY=<key>` in its environment. A lead-only emergency model (`leadEmergencyModels`, thinking suffix ignored) is refused, whether passed with `--model` or set as `defaultModel`.
With `--pane ID` (or `--workspace ID`, resolved to its only pane without an agent) the same command runs in that existing pane instead of a new tab: use it for an existing worktree session such as one another tool created. `--cwd` defaults to the pane's cwd. It refuses, writing no footer and no registry entry, when the pane is missing, runs an agent or any other foreground process, is already registered to a lane, or `--pane` and `--workspace` disagree.
The failure scan runs for every status but working (an agent that printed "No API key" or a usage-limit error and stopped at its prompt reads idle), and it skips `Tip:` lines, recalled-memory/Kibitzer blocks and echoes of the launch prompt; bare words such as `quota` count only after `Error:`.
With `--machine <label-or-id>` the lane runs on a saved herdr machine. It works with `--pane`/`--workspace` on that machine, or as a plain launch, because `herdr tab create` accepts a machine. A plain remote launch does not reuse the local `laneWorkspace` ID. The brief is read locally and copied with its footer to the target machine through the pane's shell, never by the lead's own path: launch reads the pane's shell from `herdr pane process-info` (a drive-letter cwd such as `D:\...` counts as PowerShell when no shell name is readable). In PowerShell (`pwsh`, `powershell`; 5.1 and 7) it sends one ASCII line that writes the brief as base64 bytes to `<temp dir>\dori-brief-<key>.md` and then starts the agent, so no brief character is ever parsed by the shell; any non-ASCII agent argument also travels as base64. A POSIX shell gets `printf ... > /tmp/dori-brief-<key>.md && <agent>`. A `cmd.exe` pane is refused before anything runs. The agent's prompt names that remote path. `--cwd` is the directory on the machine: it goes to the remote `herdr tab create` and is stored as `remoteCwd` (a plain launch without it stores the new pane's own directory), while the lead's `defaultCwd` is never sent there. The local MCP optimization is skipped for remote lanes.
A remote lane's footer asks it to print its `[REPORT]` lines in its own pane (the freshness sweep reads them from there) instead of messaging the lead pane, and to print `[REPORT] <key> | done | ...` instead of running `dori claim-done`, which does not exist on that machine. The lead checks the `Done =` signals and closes it with `dori close`. Local footers are unchanged.

### `dori adopt <key> --pane ID --title T --brief FILE --done "..." [--thread REF] [--cwd DIR] [--machine LABEL|ID] [--share-thread] [--allow-repo-mismatch]`
Registers a lane that is already running. Add `--machine` when the pane lives on a saved machine; `--cwd` is then its remote directory, stored as `remoteCwd`.

The lane's machine is stored in its registry entry, and every command that reads or messages the pane (`sync`, `claim-done`, `object-done`, `close`, `pause`, the watcher and supervisor) uses it. Entries without a machine stay local. For remote lanes, worktree git checks and cleanup are skipped with an explicit detail instead of being run against a local path that happens to look the same. Their `command` Done signals run on this host in `defaultCwd`, never in the remote path (older entries that stored the remote path as `cwd` included), so `dori close` works for them.

### `dori sync [--write]`
Prints `key | thread | pane | session | status` for every open lane and every unregistered agent pane, followed by drift. Read-only unless `--write`, which stores session ids.

### `dori claim-done [<key>] --evidence TEXT` / `dori object-done <key> --reason TEXT ...`
The two halves of the done flow. Both message the lane's pane and check that Enter registered.

### `dori close <key> [--note TEXT] [--force]`
Closes a lane now. Refuses (exit 2) unless every `Done =` signal reads back live. It then checks the worktrees like the watcher does: uncommitted, untracked (gitignored files don't count) or unpushed work prints `REFUSED <key>: unpushed work in <wt> ...` and touches nothing. Next it removes the worktrees; a failed removal prints `REFUSED <key>: worktree <wt> not removed: ...` and leaves the pane, thread and lane open. Only then does it mark the thread done through `hooks.threadDone` (skipped, with `thread kept open: lane <keys> still works in it`, while another open lane shares the thread), close the tab and record the lane closed. `--force` closes past unpushed work and keeps a worktree it can't remove (the watcher cleans it later).

Each close holds a per-lane lock (`lanes/<key>.close.lock.sqlite`), records its intent first (a `<key>/close/<key>` row with the note and `--force`) and runs each effect as an operation keyed by what it acts on (`<key>/worktree-remove/<path>`, `<key>/thread-done/<thread>`, `<key>/thread-archive/<thread id>`, `<key>/tab-close/<tab>` or `<key>/pane-close/<pane>`). A verified operation never runs again; a read-back that already shows the effect in place verifies it without acting. The automatic close records its intent before the lane reads `verified-done`. After a crash anywhere in the sequence, the next watcher pass (supervisor or `dori watch`) reconciles every row left attempted by reading the world back: the worktree path is gone, the pane or tab is no longer in `herdr pane list`. Done verifies it, not done allows the retry, and a hook (no read-back) becomes ambiguous. Then the close runs again with its recorded note: `LANE_CLOSED` when it finishes, urgent `OPERATION_AMBIGUOUS <id> <detail>` when it stops at an operation nobody can tell happened (the effects after it do not run), urgent `OPERATION_FAILED <id> ...` when the resumed close is refused. Each is emitted once.

Inside a lane (`DORI_LANE_KEY`, or the pane registered to a lane), `claim-done`, `object-done`, `close`, `pause` and `resume` accept only the lane's own key; another key exits 1 with `LANE_PERMISSION_DENIED`. `ack`, `handled`, `launch`, `adopt`, `hold`, `ops` and `lead-restart` are lead-only: a lane gets `LANE_PERMISSION_DENIED lane <key> may not run <cmd>; it is lead-only` and exit 1. Read-only commands, `wait`, `status`, `guard`, `can-launch`, `heavy` and `report ack` still work, and `report <key> <kind>` accepts only the lane's own key. The lead has no limit.

### `dori ops [list] [--lane KEY] [--all] [--json]` / `dori ops resolve <id> --as verified|retry`
Lists operation rows, one `OP <id> <state> attempts=<n> <updated> <detail>` line each (or `OPS none`): planned, attempted, failed and ambiguous ones; `--all` adds verified ones, `--json` prints the rows. States: `planned` (intent recorded) -> `attempted` (durable before the effect) -> `verified` | `failed` (read back not done; a later close may retry) | `ambiguous` (interrupted, and the read-back cannot tell). `resolve` is the lead's answer for an ambiguous or failed row after checking the world by hand: `--as verified` (the effect is in place; it will not run again) or `--as retry` (it did not happen; the next close runs it). Then run `dori close <key>` to finish. There is no generic undo: a wrong irreversible effect is repaired by hand (re-create the worktree from the pushed branch, reopen the thread).

### `dori report <key> <progress|question|blocked|milestone|done> --text T [--evidence E]`
A lane's structured report. Inside a lane only its own key is accepted (`LANE_PERMISSION_DENIED` otherwise); the lead may report for any lane. The text and evidence are folded to one line. It prints `LANE_REPORTED <id> <kind>` once the row is durable; routing is the supervisor's (see Lane reports under Always-on behavior). A routed row counts as hearing from the lane (`lastReplyAt`), like a thread reply.

Rows live in `<stateDir>/lane-reports.json` (`{"reports": [...]}`, rewritten under a short state lock), or on the sqlite store in the `lane_reports` table of `supervisor.sqlite`, created on first use (no schema migration):

| Field (column) | Meaning |
|---|---|
| `id` | `<lane>:<generation>:<seq>`; the routed event's journal id is `lane-report:<id>` |
| `lane` | the lane key |
| `generation` | the lane's ownership generation (design 4.2); 0 until ownership fencing lands |
| `seq` | 1, 2, 3, ... per lane, in write order (unique per lane) |
| `kind` | `progress`, `question`, `blocked`, `milestone` or `done` |
| `text`, `evidence` | one line each; `evidence` is optional (for `done` it is the claim's evidence, else `text` is) |
| `at` | write time, ms since the epoch |
| `consumedAt` (`consumed_at`) | when the supervisor routed it; unset while pending |
| `route` | `journal` (a LANE_REPORT event), `thread` (posted by `hooks.threadReply`), `claim` (done claim) or `dropped` (its lane was closed or unregistered) |

Rows are routed oldest first (`at`, then lane and `seq`) and marked consumed after the effect: a crash in between repeats it (the journal dedupes the event by id; a thread post may show twice).

### `dori report ack <id>`
Inside a lane only: confirms a supervisor message to this lane (CI follow-up), named by the ID at the end of the message. Prints `LANE_MESSAGE_ACKED <key> <id>`; an unknown ID or a message addressed to another lane exits 1. Only this ack counts as confirmation: pane activity never does, and an unconfirmed message reaches the lead after `ciConfirmMin`. A lane on another machine cannot run it; its messages reach the lead after the deadline.

### `dori pause <key> [--note TEXT]` / `dori resume <key> [--note TEXT]`
`pause` is for when the owner said wait. It works on a `working` or `not-done` lane. It sends `/goal pause` to the lane's pane, then reads the screen back until the goal command's own line appears on a line of its own: `Goal paused`, or `cannot update goal: no goal exists`, since a lane with no goal has nothing to continue. Only then does it mark the lane `paused` (recorded in its history) and, if a turn is running, send Escape and read the pane back until it is no longer `working`. The goal is paused first, so stopping the turn cannot hand off to a goal continuation. If the line does not appear, or the send fails, the lane is left as it was and the command prints `PAUSE_UNVERIFIED` and exits 3. If the goal is paused but the turn is still running after Escape, the lane stays `paused` (the sweep below keeps interrupting it) and the command also prints `PAUSE_UNVERIFIED` and exits 3; a repeat `pause` on a paused lane that reads `working` sends Escape again.

A paused lane is skipped by `freshness`: no nudge, no post. Only `dori resume` ends a pause, on the owner's word. Activity never does, because a paused lane can still be woken by a background result, a monitor event it armed before the pause, or a queued message. Every `freshness` tick that finds a paused lane `working` interrupts it again: Escape, then a read-back. If it was `working` on two ticks in a row, or Escape did not stop it, `freshness` prints `WORKING-WHILE-PAUSED` with the result (`re-interrupted, its turn stopped`, or `PAUSE_UNVERIFIED: Escape did not stop its turn`) once per working stretch (again after it goes idle and is woken, or after a new pause), so the lead can ask the owner, and the lane stays paused.

`resume` sends `/goal resume` and reads back `Goal active` the same way, then restores the status the lane had before the pause (`pausedFrom`) and restarts its quiet time, so a long pause does not turn into an instant nudge. Unconfirmed: `RESUME_UNVERIFIED`, exit 3.

Both print `PAUSED` / `RESUMED` and exit 0 on success. A lane in any other state is refused (`NOT_PAUSED` / `NOT_RESUMED`, exit 2), and a second `pause` is a no-op. `claim-done` and `object-done` on a paused lane move it out of `paused` in the registry while its goal stays paused.

### `dori supervise`
Runs supervised mode. One Discord gateway connection owns online presence, slash-command interactions and inbound messages from `discordChannels`, every thread under those channels, and open registry threads. The same process runs `watch`, `guard`, `dead-panes`, `freshness` and the lane quota check, and appends what the lead needs to act on to `<stateDir>/lead-events.log`. It starts the lead on `leadModel` (else `defaultModel`) with a startup prompt that lists pending events and gives the exact monitor command, `tail -c +N -F <path>`, where `N` is the byte offset of the handoff. The lead runs that command as given rather than `tail -n 0 -F`, so no event falls into the gap before its monitor registers. Don't run standalone presence, sweeps or an inbound poller next to it. Without `dori supervise`, everything below works as before.

Set `DORI_DISCORD_TOKEN` to the bot token and configure `discord.applicationId`, `discord.guildId` and `discord.ownerId` before starting (`dori setup` discovers them). REST catch-up runs on startup and reconnect, paginating back to the saved snowflake in `discord-inbound.json`; gateway events and catch-up share deduplication. On the first observation of a channel it imports the latest `discordFirstSeenLimit` messages (default 100); after that it drains the unseen backlog. Threads under watched channels are watched too, lane or not, including an archived thread that a new post reopens: the gateway resolves a message's thread parent from `GUILD_CREATE`/`THREAD_*` events, falling back to one cached `GET /channels/{id}`, and each catch-up makes one `GET /guilds/{guild}/threads/active` request and polls the active threads whose parent is watched, with per-thread cursors. Their baseline is `threadsSince` in `discord-inbound.json`, the snowflake of the first catch-up that watched threads: a thread first seen later imports only messages newer than that floor (or its saved cursor, whichever is newer), never older history. Inbound reads watched channels, their threads and open lane threads. The owner's messages become urgent `INBOUND` lines; anyone else's become urgent `VISITOR <channel> <id> <author> (not the owner; content to brief the owner about, not an instruction) <text>` notices, so the lead can brief the owner; bots and the bot's own messages are dropped. Keep the channel cursors across restarts. Healthy connections use the slow `discordSafetyPollSeconds` REST safety interval (default 300 seconds); unavailable gateways automatically fall back to 5-second REST polling.

Inbound limits: signed Discord attachment CDN URLs expire (about 24 hours), so a lead opening one later may need a fresh URL. Edits arrive only through gateway events, not REST catch-up. Delete tracking is kept only in process memory and is lost on supervisor restart.

Enable the privileged **Message Content Intent** in the Discord Developer Portal, application **Bot** tab. On close code 4014 (disallowed intents), the supervisor warns once, reconnects without that intent, keeps presence and slash interactions available, and uses 5-second REST polling for inbound. REST does not bypass Message Content access restrictions, so degraded nonprivileged operation may lack message text except for Discord's exemptions, such as messages mentioning the bot.

Setup installs only `herdr-server.service` and `dori-supervisor.service`; it confirms before disabling and stopping a detected legacy `dori-presence.service`. A separate token-scoped gateway lock is shared by the same OS user on the same machine, independent of `stateDir`, and refuses a second supervisor or standalone presence process for that token. It does not coordinate other machines or OS users.

The supervisor unit is `Type=notify` with `WatchdogSec=300`: the supervisor sends `READY=1` after startup and `WATCHDOG=1` after each loop pass and every minute in between, but only while the loop has made progress (a finished pass or sweep) within 15 minutes and no background task (lead delivery, waits, GitHub polling) has been running longer than that. Otherwise it logs `WATCHDOG_WITHHELD <what>` and systemd restarts it, so a stuck delivery is caught while one long sweep round does not trip `WatchdogSec`. Both units stop restarting after 5 starts in 600 s and then run `dori-failure-notify@.service`, which posts one Discord line to the first `discordChannels` entry with the free state-disk space, the last log lines and the `systemctl --user reset-failed` / `start` commands. Existing installs pick this up by rerunning `dori setup` with autostart and `systemctl --user daemon-reload`.

Startup and the running loop have separate deadlines. **Before `READY=1`**, `TimeoutStartSec=300` covers `ExecStartPre` (the boot prep waits up to 2 minutes for the herdr server) and every startup step; a start that misses it is killed with SIGKILL (`TimeoutStartFailureMode=kill`, because a blocked startup cannot run its SIGTERM handler) and restarted 15 s later, about 315 s after it began. **After `READY=1`**, `WatchdogSec=300` applies, and the supervisor withholds `WATCHDOG=1` once the loop or a background task has made no progress for 15 minutes, so a hung loop is restarted 15-20 minutes after its last progress. To name the step behind a hang, the supervisor times each startup step (`lock`, `credential`, `gateway-lock`, `supervisor` (journal and log load), `waits`, `github`, `inbound`, `ready`) and each step of the first loop pass (`loop:inbound`, `loop:heartbeat`, `loop:notice-*`, `loop:sweep:<name>`, `loop:watchdog`). It logs `STARTUP_TIMINGS ready <total>ms <step>=<ms>ms ...` after `READY=1` and `STARTUP_TIMINGS first-pass ...` after the first pass (`startup-incomplete` or `first-pass-incomplete` when it fails or stops early). A step still running after 60 s logs `STARTUP_SLOW <step> still running after 60s (budget 60s)` from a watcher thread, so the line reaches the journal even while synchronous code blocks the main thread. After a hang, `journalctl --user -u dori-supervisor.service | grep STARTUP_` shows the step.

The cold-start prompt points the lead at the full `SKILL.md`. Lead launches reuse `agentCommand` with `leadModel` (else `defaultModel`) and `leadThinking` when set, adding `--session-id` and `--session-dir` to its executable so recovery can identify the exact generation.

An idle lead is warm while its resolved session file's mtime is younger than `cacheTtlMin`; a working lead is always warm. When stale, it still receives warm delivery while any durable wait or registry lane with status `working` exists. The exception is a last recorded `message.usage.totalTokens` at or above `leadContextCapTokens`: the next stale delivery restarts it regardless of waits or lanes, which the fresh lead can read back. Missing or unreadable usage is treated as under-cap. Blocked or unclassified agents are left alone. A cold idle lead (or an available shell with no live agent) is replaced in the same pane. Only the old agent tree and processes carrying its exact session ID are stopped. Missing identity is an error, not permission for broad cleanup.

Omo's `promptCache.keepAlive` is an optional extra with roughly break-even cost; this setup does not enable it.

The default event policy (`src/event-policy.ts`, changed through `eventPolicy` with no code change) marks owner inbound and visitor notices, lane done/not-done/closed, remote lane blockers and questions (`LANE_REPORT`), dead and unrecognised panes, `NO-REPORT`, `NO-PROGRESS`, guard alerts and clears, `LAUNCH_READY`, working-while-paused, wait completion/timeout, `SUPERVISOR_STUCK`, `ACK_MISSING`, `UNHANDLED`, `LANE_QUOTA_STALL`, `INBOUND_EDIT`, `INBOUND_DELETE`, `LANE_QUOTA_CLEARED`, `LANE_QUOTA_UNKNOWN`, `LANE_RECOVERY_EXHAUSTED`, `LANE_RECOVERY_BLOCKED`, `LEAD_QUOTA_EXHAUSTED`, `LEAD_QUOTA_CLEARED`, `LEAD_EMERGENCY_APPROVAL`, `QUOTA_GATE_UNKNOWN`, `WAIT_FAILED`, `WAITS_CORRUPT`, `OPERATION_AMBIGUOUS`, `OPERATION_FAILED` and `CLAUDE_QUOTA brief|blocked` as urgent. An urgent event starts a delivery. Every other event remains in the durable inbox as digest and joins the next urgent batch, or is delivered on its own once the oldest one has waited `digestMaxDelayMin`.

The sweeps (`watch`, `guard`, `dead-panes`, `recover`, `freshness`, `quota`, `claude-quota`, `memory`, `lead-pane`) run every 30 seconds, each on its own: their lines are enqueued as they appear, and a sweep that throws (for example a failed `herdr pane list`) becomes one digest `SWEEP_WARN <sweep> <reason>` (`LANE_WATCH_WARN` for the watcher) and never stops the other sweeps or the supervisor. The same warning is queued at most once an hour, and warnings (any `*_WARN` line, including `DEAD_PANES_WARN` for an unreachable remote machine, whose quiet lanes still raise urgent `NO-REPORT`/`NO-PROGRESS`) never trigger the `digestMaxDelayMin` delivery on their own; stderr logs every occurrence. The watcher writes a claim's announced flag only after `LANE_DONE_CLAIMED` is enqueued. Large startup batches use a private `@file` prompt to avoid terminal input limits.

`supervisor.json` is the durable inbox and restart transaction. `lead-events.log` contains one JSON event per line (`id`, `line`); its stable IDs are the delivery receipts. Delivery means reaching this durable transport or a positively confirmed startup prompt, not that the LLM has completed the requested work. Keep both files and `discord-inbound.json` across supervisor restarts. One OS-backed lock prevents simultaneous writers and is released on process exit, including a crash. An uncertain launch retains its transaction and verifies the same session on restart; it never blindly submits the prompt again. `STARTUP_UNCONFIRMED` requires inspecting that exact session before intervening; after 5 unconfirmed checks of one session that never wrote startup evidence (below) the supervisor saves the lead pane's last 80 lines to `lead-pane-<pane>-<ms>.txt` in the state dir (`LEAD_PANE_SCREEN_SAVED <pane> <path>`), kills only that session's process tree, replaces the pane when only a plain shell is left in it (`LEAD_PANE_RECREATED`, otherwise `LEAD_PANE_KEPT`), and moves the same events to a fresh session id. A pane that vanished while a launch was submitted gets a fresh session id too. A launch is typed only into a plain shell: any other foreground process (an agent started by hand, for example) fails it with `LEAD_PANE_BUSY` and the retry backoff. A launch also needs startup evidence for its exact session within 20 seconds (`session-holders/<session>/<pid>.json` or the session jsonl); without it the supervisor kills only that session's process tree and relaunches once with a fresh session id, the same events and the same tail offset (`LEAD_STARTUP_HUNG_RETRY`). A second miss logs `LEAD_STARTUP_HUNG <session>`, retains the events and leaves the next relaunch to the normal retry backoff. SIGINT/SIGTERM stop polling and release the supervisor lock without terminating the lead.

**SQLite store.** `dori store import` moves a state dir to the store: stop the supervisor first (it refuses with `STORE_SUPERVISOR_RUNNING` while the supervisor lock is held). It records the source cursors (size and sha256 of `supervisor.json`, of `lead-events.log` up to its last complete line, and of `github-events.json`), imports every journal field and every delivery from `lead-events.log`, reads the result back and refuses with `STORE_IMPORT_MISMATCH` unless it equals the source field by field (`STORE_IMPORT_UNKNOWN_FIELD` for a field it has no table for). Only then does `supervisor.sqlite` appear, and `supervisor.json` becomes the read-only `supervisor.json.pre-sqlite`; `github-events.json` moves into the same database (tables `gh_repos`, `gh_prs`, `gh_issues`, `gh_cache`) and stays as the read-only `github-events.json.pre-sqlite`. A state dir imported before that keeps its `github-events.json` until the first sqlite supervisor start, which imports it the same way under its lock. A refusal leaves the state dir untouched. Then set `"store": "sqlite"` and start the supervisor. `lead-events.log` stays the lead's transport; the store also records each delivery and the log offset it has read, so a restart reads only the log tail and delivers nothing twice. Owner messages (`INBOUND`, edits and deletes) are synced to disk before `enqueue` returns; other writes survive a process crash at once and power loss by the end of the loop pass. `dori status` and the emergency approval read whichever store holds the journal.

**Rollback (`dori store export`).** With the supervisor stopped (`STORE_SUPERVISOR_RUNNING` otherwise), it writes `supervisor.json` and `github-events.json` back from the store and makes `lead-events.log` hold every delivery the store recorded. The sqlite supervisor keeps appending `lead-events.log` as before (it is the lead's transport and the compatibility log), so the log normally stays byte for byte as it was and the lead's tail offset stays valid; a recorded delivery it lacks is appended, and events the store pruned to tombstones are still lines of the log, which a json supervisor recovers at its start. Each file is read back and must equal the store (`STORE_EXPORT_MISMATCH` otherwise, nothing moved into place); `supervisor.json` is written last, and the database becomes the read-only `supervisor.sqlite.exported` (with its `-wal`/`-shm` files, if any). The report lists what it wrote (size and sha256 of each file) and the store's source cursors (log offset, last GitHub poll, the import record). It refuses a state dir that already has `supervisor.json` or a `supervisor.sqlite.exported` (`STORE_EXPORT_EXISTS`). Then set `"store": "json"`, deploy the previous SHA if rolling back, and start the supervisor.

**Retention (sqlite store).** Unresolved work is never pruned: undelivered events, the events of tracked owner messages (open, acked, quarantined or handled within the last day), a pending restart's events, and open PRs. Once an hour the supervisor moves delivered event bodies older than 7 days to dedupe tombstones (id and time), so a replayed source id is still a duplicate; event and owner tombstones expire after 90 days. GitHub status history keeps 30 days: a closed or merged PR quiet that long keeps its baseline row without its activity ids, and a cached response no poll used for 30 days is dropped. Cached GitHub responses keep only the fields the poll reads. The json journal keeps everything, as before.

A transient lead state (pane missing, old lead not exited, startup or launch admission unconfirmed, session unresolved, non-agent foreground process) does not end the supervisor: it logs one `SUPERVISOR_RETRY` line, keeps events and the restart journal as they are, retries with backoff of 5s doubling to 60s, and recreates a missing lead pane as a `dori-lead` tab in the `Dori` workspace at `defaultCwd` (herdr removes a workspace with its last pane, so a missing `Dori` workspace is created again and its first pane becomes the lead), writing the new `leadPane` back to the loaded config; a herdr refusal is logged as `LEAD_PANE_CREATE_FAILED <reason>` and retried with the backoff. After 10 minutes of the same failure it queues one urgent `SUPERVISOR_STUCK <reason>` and posts it once to the first `discordChannels` entry, scrubbed of home paths and pane ids like every automatic post (the lead's copy keeps them); config errors and a held lock still exit.

**Quota stalls.** A stall needs both signals: the pane's last 40 lines carry a quota failure (omo's `All ... accounts for <provider> are currently blocked`, a line starting `Usage limit reached`/`Rate limit exceeded`, or quota words after `Error:`; tips, recalled-memory/Kibitzer blocks and echoed briefs are skipped as for startup failures), and `quotaCheck` for the model's provider lists accounts that are all blocked. One blocked account next to a healthy one is omo's own account fallback, not a stall. The `quota` sweep checks each working local lane (its `model`, else `defaultModel`) and queues urgent `LANE_QUOTA_STALL <key> <pane> <reason>` once per stall; the note clears when the lane recovers. It never types into the lane or changes its model. Remote lanes are skipped, since the check reads this host's accounts.

A stall now auto-pauses the lane and reports `LANE_QUOTA_STALL <key> <pane> reset=<ISO|unknown> <N/M provider accounts blocked>: <line> | PAUSED ...`; with a known reset it registers the wait `quota-<key>`. When quota returns it sends `LANE_QUOTA_CLEARED <key> <pane> ...` and resumes the lane only if this sweep paused it. An unreadable quota check is `LANE_QUOTA_UNKNOWN` and changes nothing. Freshness skips a stalled lane.

With more than one `leadModel` entry the supervisor also watches the lead. Before each urgent delivery, and every 30 seconds otherwise, it reads an idle lead's screen; on a stall it cold-restarts the lead on the next entry, the same handoff as any cold restart (pending events in the prompt, the tail offset after them), and tells the new lead why, so it re-checks the last events the stalled one may not have handled. A fresh launch that comes up stalled is stopped (exactly its session) and relaunched on the next entry with the same events. A busy or blocked lead is never interrupted. The current entry is saved in `supervisor.json`, and every `leadPrimaryRetryMin` the first entry's provider is checked; once it is unblocked the idle lead moves back. Each completed switch posts one plain line to the first `discordChannels` entry. When the last entry is stalled too, the existing unconfirmed and `SUPERVISOR_STUCK` handling applies. With a single lead model none of this runs.

When the last lead model is stalled (or the only `leadModel`), the owner gets one line and the lead one urgent `LEAD_QUOTA_EXHAUSTED <model> reset=<ISO|unknown> ...`; the end of it is `LEAD_QUOTA_CLEARED <model> ...`. A working lead stalled for `leadQuotaBusySwitchMin` with a non-emergency fallback left is stopped and switched. A paid emergency model is never used without the owner's approval: next to `LEAD_QUOTA_EXHAUSTED` the lead gets `LEAD_EMERGENCY_APPROVAL <model> ...` and the owner one line asking for `/emergency`; a working lead is never forced onto it. A lead on a fallback that is itself stalled goes back to the first model as soon as that has quota, working or not, and a cold start that comes up blocked on the last usable model counts as started, so quota control owns it instead of `STARTUP_UNCONFIRMED` retries. Owner announcements (model switches, exhaustion, approval requests, stuck restarts) go through a durable outbox in `supervisor.json`, retried every minute until posted. A cold start always lists the held launches (`LAUNCH_QUEUE ...`), even after `LAUNCH_READY` lowered the hold flag. Owner edits and deletes revise the tracked message: reminders and cold handoffs carry the latest text, an edit of a handled message is tracked again, and a deleted one counts as handled and is never handed over. Messages handled more than a day ago leave the tracking list for a tombstone. Returning to the first model needs `leadPrimaryReturnChecks` clean checks in a row. All three lead-quota keys are checked when `dori supervise` starts, before it takes the lock: a bad value stops it with `leadQuotaBusySwitchMin must be positive`, `leadStuckRestartMin must be positive` or `leadPrimaryReturnChecks must be a positive integer`. When Claude usage can't be read, `QUOTA_GATE_UNKNOWN <detail>; the Claude quota gate is off (fail-open) ...` goes to the lead and, as `Dori warning: ...`, to the owner, once per episode. A lead that stays busy with unread owner messages for `leadStuckRestartMin` is cold-restarted with them (`LEAD_STUCK_RESTART` in the log) and the owner is told.

An owner message that has not reached a running lead within a minute (delivery failing, or a cold start that has not confirmed) gets `ownerDelayNotice` posted once in its own channel or thread; the message itself stays queued.

**Read receipts.** Every owner `INBOUND` the supervisor appends to the lead's log waits in `supervisor.json` (`awaitingAck`) for the lead's `dori ack`. A message still unacked `ackTimeoutSec` after the handover is reminded once with urgent `ACK_MISSING <channel> <messageId> (...)` so the lead wakes; every message that falls due in the same check shares one event, its entries joined by ` | `, so an incident costs one wake instead of one per message; after a second window the owner gets `ackMissingNotice` once in that channel or thread. Nothing escalates while a lead restart runs, and when a cold start confirms (`LEAD_RESTARTED`) every waiting message gets a fresh window, so a slow boot never counts against the new lead and a message the old lead missed is reminded to the new one; a notice already posted is never repeated. `dori status` shows messages reminded and still unacked as a problem (`unacked N`). Entries and stray ack files are dropped after a day.

**Tracking comes from rows, not history.** At startup the supervisor reads owner tracking from its stored rows (`awaitingAck`, `closedOwners`; the sqlite store's `owner_messages` and `owner_tombstones`), which keep every unresolved message regardless of age with its coverage, revisions and deletion state. An owner `INBOUND` (or edit) in the event history with neither a row nor a tombstone, as after a tracking reset, gets a `quarantined` row: the lead gets one digest-priority `OWNER_QUARANTINED <count> <channel>:<id>,<id> ...` listing all of them once, and they are never reminded, never posted to the owner as delayed and never handed to a new lead. `dori ack`, a new edit or a delete turns a quarantined message into an ordinary tracked one.

**Handling.** An acked owner message stays tracked until `dori handled` covers its task count (default 1). After `handledTimeoutMin` without full coverage the lead gets urgent `UNHANDLED <channel> <messageId> coverage=<linked>/<tasks> <original event>`; `ACK_MISSING` carries the same body. Both bodies are redacted and cut to 2000 characters. Another window later the owner gets `unhandledNotice` once. Unfinished owner messages are never dropped and join every cold-restart handoff.

### `dori memory check`
Read-only check of the lead's memory (`memoryCheck`); it never writes the memory repo. Prints `MEMORY_FILE`, `SIZE <bytes> (<KB>), limit <KB>: ok|OVER by <KB>`, `OPEN_ITEMS <n>`, one `STALE #<n> "<item start>": <refs>` per Open item (a top-level bullet under `## Open`, with its indented lines) that names finished work, `UNCHECKED <ref>: <why>` for references it could not verify, and a last `MEMORY_CHECK action needed|clean` line. Finished work: a closed lane (a lane in `<stateDir>/lanes-archive/`, or a file hand-moved to the old `<stateDir>/lanes-closed`, now `lanes-archive/legacy/`, whole-word key match, never a key that is open again) or a merged PR (`owner/repo#N`, a github.com pull URL, or `PR #N` when the item names exactly one repo as `owner/repo` that is watched, named in a lane's Done signal, or under one of their owners; checked with `gh pr view`). Exit 0 when clean, 1 when `human.md` is over the limit or an item is STALE, 2 when it cannot check (memory not found, bad usage).

Under `dori supervise` the `memory` sweep runs the same check once every 24 hours and 15 minutes after a newly closed lane is first seen (so the lead's own cleanup turn comes first). Findings become one digest `MEMORY_CHECK <findings> (run dori memory check, then condense or delete them)` line for the lead, sent again only when the findings change; a missing memory repo is `MEMORY_CHECK_WARN <reason>`, retried on the next turn. State: `<stateDir>/memory-check.json`.

### `dori ack <channel> <messageId> [--tasks N]`
The lead's read receipt on a Discord owner message: removes the bot's hourglass (a missing one is fine), adds the eyes, then writes `<stateDir>/acks/<channel>-<messageId>.json` for the supervisor to consume. The ack is recorded only after the eyes are on the message, so a failed reaction exits non-zero and leaves the message to be reminded. Ids are the two numbers in the `INBOUND` line (for a thread message, the thread id is the channel). Uses `DORI_DISCORD_TOKEN`. `--tasks N` declares how many separate tasks the message holds (see `handled`).

### `dori handled <channel> <messageId> [--tasks N] [--lane KEY ...] [--reply]`
Declares what covers an owner message: each distinct `--lane` (it must exist in the registry) covers one task, and `--reply` covers one more. At least one of them is required. `--tasks N` sets the task count for a message with several requests, such as work in several projects; it defaults to 1 and only grows. Prints `HANDLED_LINKED <channel> <messageId>`, which means the link was recorded, not that every task is covered. Coverage is your declaration, not proof the lane finished. It changes no reactions.

### `dori recover [key]`

Runs the supervisor's lane recovery immediately, for one key or all working lanes. A missing pane is recreated using its recorded brief, cwd and model. A restored `omo` without `--model`, or with a model different from the registry, is also replaced on the recorded model before freshness can nudge it. Matching live panes and paused or closed lanes are left alone. Recovery attempts are bounded and persisted in the registry; each successful recovery posts one explanation in the lane's thread. A lane with a recorded session is relaunched on that session (`LANE_RECOVERED ... session-resumed`), else from its brief. If the lane's provider or the Claude gate is blocked, nothing is launched and urgent `LANE_RECOVERY_BLOCKED <key> <pane> ...; not relaunched` is sent once per reason. After the last attempt fails, urgent `LANE_RECOVERY_EXHAUSTED <key> <pane> ...` is sent once; `dori status` marks the lane `!RECOVERY-EXHAUSTED` and `dori doctor` fails its `lane recovery` check.

### `dori lead-restart [--model ID] [--thinking LEVEL]`

Records a durable cold-start request in `lead-restart.json`. The next idle supervisor delivery honors it even without traffic and below both context caps; a working, blocked or unknown lead is never interrupted. The request captures the current configured model chain, so editing `leadModel` then running `dori lead-restart` takes effect without restarting the supervisor. Overrides apply only to the lead. `status` and `doctor` show the pending request until startup confirms; a newer request arriving during startup stays pending. A missing lead pane is recreated by the supervisor before the request runs.

### `dori wait <key> --until SIGNAL --note TEXT [--thread REF] [--every SEC] [--timeout MIN]`
Registers a durable follow-up for `dori supervise`, using the same signal syntax as `Done =` (`merged`, `closed`, `published`, `command`, `file`, `url`). Checks default to every 60 seconds with a 10-second bound; relative file paths and commands use the registration directory. `--timeout` is an optional deadline in minutes. Completion emits urgent `WAIT_DONE <key> <note>`; expiry emits `WAIT_TIMEOUT <key> <note>`, with `thread=REF` when supplied. The wait is then removed. State in `waits.json` survives lead, supervisor and machine restarts; keep it with the supervisor inbox and event log for deduplication. A failed check leaves the wait registered. A check that throws or times out counts as a failure; a wait with no `--timeout` that fails `waitMaxFailures` times in a row (default 30) ends with urgent `WAIT_FAILED <key> <note> (...)`. A `waits.json` that won't parse is moved to `waits.json.corrupt-<ms>` and reported once as urgent `WAITS_CORRUPT`; every wait in it has to be registered again.

`dori wait --list` prints JSON. `dori wait --cancel <key>` removes a wait; cancel before reusing an existing key.

### `dori emit <KIND> --text T [--id ID]`
Spools one event `<KIND> <T>` in `<stateDir>/emit/` for the supervisor's `emit` source. Its class comes from `eventPolicy` like any other kind (unknown kinds get `eventPolicy.default`). With `--id` a repeat of the same id is dropped by the journal's dedupe; without it every call is its own event. `KIND` is uppercase letters, digits and underscores, and may not be a built-in kind (`INBOUND`, `LANE_*`, `WAIT_*`, `GH_PR`, `SOURCE_FAILED`, ...), so no source can pass itself off as the owner or a lane. Prints `EMIT_QUEUED emit:<id>`.

### `dori source list [--json]` / `dori source add <name> --type poll|webhook|file ...` / `dori source remove <name>`
Lead-only. Manages `<stateDir>/sources.json` (mode 0600; the supervisor rereads it every polling pass, so no restart and no code change). `list` shows every source, built-ins first, with its events, dropped duplicates, last event kind and time, and its error while failing; a webhook secret is never printed. Kinds follow the `dori emit` rules.

- `--type poll --command CMD --every SEC --match RE --kind KIND [--cwd DIR]`: runs `CMD` (a shell line run with `sh -c`, or a JSON argv array) every `SEC` seconds (at least 5, killed after 30 s). Each stdout line matching `RE` is one event `<KIND> <line>`, deduped by the first capture group of `RE` when it has one, else by the whole line, so a poll runs for ever and reports each match once. A non-zero exit is a failure of this source only.
- `--type webhook --port P --kind KIND [--secret S]`: listens on `127.0.0.1:P` only. A `POST` carrying `X-Dori-Secret: S` (or GitHub's `X-Hub-Signature-256` HMAC of the body) is one event: the JSON body's `text` (else the raw body, up to 64 KB), deduped by the body's `id`, an `X-Dori-Id` or `X-GitHub-Delivery` header, else the body's hash. It answers `202 {"ok":true,"duplicate":false}` only after the event is journaled, `401` for a wrong or missing secret (counted as `rejected`), `405` for other methods. Without `--secret` one is generated and printed once. To receive from outside the machine, put a separate tunnel in front of it; never route it through the owner's remote-access cloudflared.
- `--type file --path FILE --match RE --kind KIND`: tails `FILE` from its end at first sight (no history flood); each new complete line matching `RE` is one event. The read position survives restarts in `sources-status.json`, and a truncated or rotated file is read again from the start.

### `dori schedule add <name> ...` / `dori schedule list [--json]` / `dori schedule remove <name>` / `dori schedule run-now <name>`
Lead-only. Scheduled jobs: `schedule` sources in `<stateDir>/sources.json`, run by the supervisor's polling pass. Kinds follow the `dori emit` rules.

- `add <name> (--cron EXPR | --every SEC) (--text T | --command CMD [--cwd DIR] [--heavy] [--timeout SEC]) --kind KIND [--tz ZONE] [--catch-up once|skip]`. `--cron` takes 5 fields (minute hour day-of-month month day-of-week: `*`, `N`, `N-M`, lists and `/STEP`; with both day fields restricted either one matching fires, as in cron) or `@hourly`, `@daily`, `@weekly`, `@monthly`, read in `ZONE` (default `Asia/Seoul`). `--every` is at least 60 seconds, counted from when the job was added. No slot before the job was added ever runs. A `--text` job journals `<KIND> <T>`. A `--command` job (a shell line run with `sh -c`, or a JSON argv array; killed after `--timeout`, default 600, at most 3600 seconds) journals `<KIND> <name>: <output>` on exit 0 and `SCHEDULE_FAILED <name> exited <code>: <output>` otherwise (digest unless `eventPolicy` says else); a failed run is reported, not retried. `--heavy` runs the command only in a free heavy slot (`heavySlots`, `heavyMaxLoad`, the same slots as `dori heavy`): a due heavy job waits, pass by pass, without blocking the other sources, and keeps its slot until it finishes. Prints the job and `SCHEDULE_ADDED <name> next <time> KST`.
- Each slot is one operation row, recorded before it runs and never planned twice, so a supervisor restart never repeats a run. A slot found more than 5 minutes late, or several slots passed while the supervisor was down, follows `--catch-up`: `once` (default) runs the newest missed slot once, `skip` records it as skipped. A crash while a command ran leaves the row `attempted`: on the next start the journal decides. The result is there: verified. A `--text` job without it emits again (the event id dedupes it). A `--command` job without it becomes `ambiguous` with one urgent `OPERATION_AMBIGUOUS <id> ...`, and the command does not run again until `dori ops resolve <id> --as verified|retry`.
- `list` shows each job with its schedule, next run, last run and result; `remove` deletes it (its rows stay in the store); `run-now` queues one run in `<stateDir>/schedule-now/` that the supervisor runs on its next pass as its own row (`now@<time>`), leaving the schedule as it was.

### `dori watch`
Runs forever. Every 30 seconds it prints each new claim once (`LANE_DONE_CLAIMED`). Claims older than `closeAfterMin` are settled: unpushed or uncommitted work and failing signals turn into objections (`LANE_NOT_DONE`); otherwise the lane is closed (`LANE_CLOSED`). The deadline lives in the registry, so a restart picks up where it left off. The window starts at delivery to the lead, and an `autoClose: machine` lane prints `LANE_AUTO_CLAIMED` and `LANE_AUTO_CLOSED` (see Claim delivery under Always-on behavior). One lane's error prints `LANE_WATCH_WARN <key> <reason>` and the other lanes are still watched.

For a remote lane (working or not-done) it reads the newest `[REPORT]` line in its pane. A new `done` report becomes the claim the lane cannot make itself (`dori claim-done` with that evidence: same window, same live re-check, remote worktree checks skipped); a new `blocker` or `question` prints urgent `LANE_REPORT <key> <kind> <text>`. Each distinct line is acted on once, so an objection tells a remote lane to print a done line with updated evidence, and its footer says the same. Lines whose text starts with `<` are the footer's placeholders and are ignored.

Cleanup sweep: for a closed lane whose close receipt lists a worktree as kept (it could not be removed then, typically untracked files), the watcher removes it once `git status --porcelain` is clean, only under `worktreeRoot`, and prints `WORKTREE_CLEANED <key> <paths>`; a failed removal is a `LANE_WATCH_WARN`. Open lanes (working, not-done, paused, done-claimed) are never touched, whatever their PRs say.

### `dori freshness [--loop MIN]`
For lanes that have gone quiet: after `nudgeAfterMin`, a lane herdr reports as `working` is never nudged. Its pane is read (no model turn) and the in-progress todo item is posted to its thread through `progressTemplate`, scrubbed: at once when the item changes, and again every `nudgeAfterMin` while it does not. A post counts only when the hook exits 0; otherwise it is retried on the next tick and `PROGRESS-FAILED` is printed once per distinct error. When nothing can be posted (no Todo item on the pane, or no `threadReply` hook) it prints urgent `NO-PROGRESS` once per silence. Only an idle silent lane gets the pane nudge. Then the lane's last `[REPORT]` line posted to its thread after `postAfterMin`, with home paths and pane ids scrubbed. The nudge, `NO-PROGRESS` and the report post each happen once per silence; only the todo post repeats. The line is posted only once it is still the last `[REPORT]` line on the next tick (`PENDING-REPORT` the first time) and differs from the line posted last time (`STALE-REPORT` otherwise). A held-back outcome is printed once per change, not on every tick. A nudge reports its delivery as `delivered` (the agent status moved to working) or `unconfirmed`.

A lane's `dori report` rows are its progress (the router posts them): a working lane with a row newer than `nudgeAfterMin` costs the freshness sweep no herdr call. Its pane is read as above only once no row arrived within `nudgeAfterMin`, and its silence counts from its newest row or reply. Lanes that never write rows keep the screen-based progress and nudge.

### `dori dead-panes [--loop MIN]`
Prints `DEAD_PANE <id>` once per hour for a pane with no running agent status whose last lines match `deadPanePatterns` on two ticks in a row with the same text. A pane herdr reports as idle, working, blocked or done is never dead. A pane that is neither is unrecognised; three unrecognised ticks in a row print `UNRECOGNISED_PANE <id> ...` once (list non-agent panes in `ignorePanes`).

### `dori guard [--loop MIN]`
Prints `HOST_GUARD ALERT <reasons>` when load, free memory, free disk or the pane count crosses its threshold, and `HOST_GUARD CLEAR` when it recovers. It also prints `COMPUTE_READY` / `COMPUTE_BUSY` as load crosses `loadOk`. Only changes are printed. Under `dori supervise` it also prints urgent `LAUNCH_READY` once when `dori can-launch` (or a held `launch`) last answered HOLD and the host now passes the same check and the cached Claude quota gate is `ok`, so held work is started without waiting for anything else. The line ends with the queue: `; queued launches (N): <key> cwd=.. repo=.. thread=.. machine=.. done="..." brief=<path> queued <iso>; ... (dori hold list)`.

### `dori hold list` / `dori hold drop <key>`
`list` prints the launches waiting after a HOLD as JSON. `drop` removes one and prints `HOLD_DROPPED <key>`, or exits 1 when the key is not queued.

### `dori quota [--json]`
Reads Claude usage now (pi-quota, no session or model turn) and prints one line, `QUOTA <mode> | Claude headroom N% (hold-lanes < 50%, brief < 25%)`, plus `; clears MM-DD HH:MM KST` when the mode is not `ok`, then one `| <account> N%: 5h L% left / T% time = H% (resets MM-DD HH:MM KST), 7d ...` part per Claude account (quota left, time left until the reset, and that window's headroom; the account's N% is its tightest window), then pi-quota's own block. `--json` prints the verdict (`mode`, `reasons`, `resetAt`, `holdsLanes`, `headroomPct`, `holdLanesPct`, `briefPct`, and `accounts` with each window) and `usage`. Every Claude account counts: their headroom adds up (see `quotaGate`). Without a Claude account it prints `QUOTA unknown`. Every read refreshes `<stateDir>/claude-quota.json`.

### `dori can-launch [--model M]`
Prints `CAN_LAUNCH` and exits 0 when the host has room for another lane. Otherwise it prints `HOLD <reasons>` and exits 4. The reasons come from the guard's memory, disk and pane-count thresholds, and from the Claude quota gate (`quota hold-lanes: Claude 5h 85% >= 80%, resets 10-22 15:10 KST`, ending in `; near reset: 5h hold at 95% (resets in 25m)` near the 5h reset; a launch the near-reset line lets through prints `QUOTA <mode> | near reset: 5h hold at 95% (...); launch not held` on stderr) when the lane's model (`--model`, else `defaultModel`) spends the Claude subscription. A usage read that fails is warned on stderr and never holds. CPU load alone never holds a launch, because it moves too fast to plan around. A HOLD leaves `<stateDir>/launch-hold.json` behind (its blocked flag is lowered by the next `CAN_LAUNCH`, or by the supervisor when it sends `LAUNCH_READY`; queued launches stay), so run it when you are about to launch, not as a status probe: every HOLD answer is read as queued work.

### `dori send <slack|telegram|discord> --to TARGET --text TEXT [--thread ID] [--edit ID]`
Posts a message, or edits one with `--edit`. `--to` is a plain id or a lane thread ref (`platform:parent/thread`, as in `lane.thread`), so the default hooks can pass `{thread}` straight in: Discord posts to the thread id, Telegram to the chat and topic, Slack to the channel and thread ts. An explicit `--thread` wins; on Discord, `--to <channel> --thread <thread>` posts in the thread. Tokens come from `DORI_SLACK_TOKEN` (plus `DORI_SLACK_COOKIE` for a user token), `DORI_TELEGRAM_TOKEN` or `DORI_DISCORD_TOKEN`, read from the process environment first and then from `~/.dori/env` (the supervisor's EnvironmentFile), so a lead that did not inherit them still sends. A token missing from both exits non-zero with the error on stderr, which means the message was not delivered. Text containing `$(` is refused, since it can only come from a shell string. Rate limits are retried with the server's wait time; other errors fail at once.

Inside a lane, `dori send` (and `--edit`) may target only the lane's own thread; anything else, or any target for a lane with thread `none`, exits 1 with `LANE_PERMISSION_DENIED`.

### `dori presence <slack|discord>`
Keeps the account shown as online until stopped.
- **Discord (non-supervised installs):** the bot connects to the gateway, identifies as online and handles `/quota` when `discord` is configured. Supervised installs use `dori supervise` for all three. The shared token-scoped machine/user lock refuses to start presence while a supervisor or another presence process owns that bot token.
- **Slack, user token:** it opens one web-client-type socket and tickles it every minute. Slack shows a user active only while such a socket is open, and auto-aways an idle one after about 30 minutes.
- Run one instance per account. Two writers flip each other's presence.

### `dori inbound slack [--loop MIN]`
Prints `INBOUND <source> <channel> <thread> <ts> <user> <text>`. It reads from three places, each message once:
- `threads-view`: unread replies in threads the account follows (Slack's own Threads view);
- `own-thread`: new replies in any thread the Dori posted in, tagged or not;
- `unread`: DMs, group DMs and channels with unread mentions.

The Dori's own messages and bot messages are skipped. Every message the Dori posts records its thread in `<stateDir>/slack-threads.json`, whichever helper sends it, so a guest's untagged reply under a root posted with a raw API call is still found.

### `dori transcribe <audio-file>`
Runs `hooks.transcribe` and prints the transcript. A failed or empty transcription is an error, never an empty message.

### `dori heavy <label> -- <command ...>`
Waits until load is under `heavyMaxLoad` and one of `heavySlots` is free, then runs the command and frees the slot when it exits. A slot held by a process that no longer exists (or a zombie) is taken over. Use it for full builds and test suites. Installs, focused tests and git do not need it.
